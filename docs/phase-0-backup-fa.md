# شناخت بکاپ و ابزار JVM — فاز صفر

> دربارهٔ ریسک مرز تراکنش Room/DataStore، [بررسی بومی جدید](phase-0-native-storage-fa.md) را نیز ببینید؛ بازگرداندن وضعیت وب در حافظه لزوماً بازگرداندن ذخیرهٔ بومی نیست.

## قالب و مسیرهای قدیمی مشاهده‌شده در `assets/index.html`

| مسیر/تابع | شواهد و رفتار |
|---|---|
| `exportFullDatabaseJson` | شیء JSON با `app: "stayar"`، `kind: "full"`، `version: 2`، `exportedAt` و `state`. نسخهٔ پاکت را با `state.version` اشتباه نگیرید. |
| `exportProjectJson` | همان ساختار پاکت با `kind: "project"` و کلید `project`. |
| `normalizeState` | پروژه‌ها را پس از پالایش به حداکثر ۱۰۰ محدود می‌کند؛ آرایه‌ها و حضور پیش‌فرض می‌دهد؛ `activeProjectId` نامعتبر را به نخستین پروژه برمی‌گرداند؛ `onboarding` و `coachDismissed` را نیز تنظیم می‌کند. |
| اصلاح بکاپ قدیمی | فقط زمانی که حالت ورودی native نباشد، `state.version` وجود داشته باشد و کمتر از ۳ باشد، ضریب اضافه‌کار **دقیقاً ۱٫۴** به ۱ تبدیل می‌شود؛ سپس `state.version` برابر ۳ می‌شود. پاکت بدون نسخهٔ state به‌تنهایی کافی نیست. |
| `sanitizeProject` | تاریخ‌ها و شناسه‌ها پالایش، بعضی متن‌ها محدود و مبالغ از بالا clamp می‌شوند؛ از هر آرایه حداکثر ۵۰٬۰۰۰ رکورد و از روزهای حضور حداکثر ۵٬۰۰۰ روز حفظ می‌شود. ورود مقادیر نادرست همیشه به معنی رد بی‌تغییر نیست؛ اصلاح‌ها پیش از اعتبارسنجی انجام می‌شوند. |
| `importBackupText` | برای بکاپ کامل `obj.state` و در غیر این صورت خود شیء را normalize می‌کند؛ برای پروژه، `project`، یا نخستین عضو `projects`، یا خود شیء را می‌پذیرد؛ شناسهٔ پروژهٔ واردشده جدید و قفلش باز می‌شود. |
| جایگزینی | ابتدا اعتبارسنجی سمت وب و در صورت وجود پل، `nativeDryRun` اجرا می‌شود؛ سپس تأیید، `replaceWholeState`، و پیش از تغییر، `ensureSafetyCopy`. در صورت شکست ذخیره، متغیر وضعیت قبلی بازگردانده می‌شود. |
| بکاپ اضطراری / خودکار | `restoreRecovery` و `restoreSnap` قبل از جایگزینی از همان مسیر ایمنی استفاده می‌کنند. قبل از بازگردانی recovery، نمونهٔ قبلی آن حفظ می‌شود تا بعداً دوباره قابل استفاده باشد. |

این موارد توصیف سورس وب‌اند؛ اعتبارسنجی native، تراکنش Room و خطاهای واقعی ذخیره‌ساز هنوز به‌صورت جامع با اجرای APK آزموده نشده‌اند. به‌ویژه نباید سقف‌های sanitization و validation را با محدودیت‌های فرم اشتباه گرفت. بررسی تفصیلی بازیابی و آزمون round-trip با دادهٔ واقعی همچنان باقی است.

## خوانندهٔ Kotlin برای goldenها

فایل `parity/kotlin/GoldenReader.kt` ساختار JSON و هش APK را بررسی می‌کند؛ اعداد JSON با `BigDecimal` خوانده می‌شوند. تعدادی ورودی JSON درست و نادرست نیز بررسی می‌شود. این **موتور مالی، ماژول domain یا مقایسهٔ خروجی Kotlin با JavaScript نیست**؛ همهٔ محاسبات واقعی موتور جدید هنوز انجام نشده‌اند.

دستور اجرای خواننده با JDK 17 و کامپایلر Kotlin JVM:

```sh
JAVA_HOME=/path/to/jdk KOTLINC=/path/to/kotlinc ./parity/tools/check-kotlin.sh
```

در این محیط JDK 17.0.9 از بستهٔ موقت PyPI `jdk4py==17.0.9.2` و کامپایلر موقت npm `kotlin-compiler@2.4.21` خارج از مخزن نصب و ابزار فوق با موفقیت اجرا شد. این ابزارها جزو پروژه یا نصب استاندارد Gradle/Android SDK نیستند. خروجی: ۵۸۵ نمونه خوانده شد و هش APK تأیید شد. نسخه‌های نهایی ساخت Android و Gradle بعداً باید مطابق پروژهٔ واقعی انتخاب و قفل شوند.

## آزمون‌های افزوده‌شده

`cd parity && npm ci && npm test` علاوه بر نمونه‌های قبلی، با seed ثابت ۱۰٬۰۰۰ تخصیص و ۱۰٬۰۰۰ تقسیم واریزی را روی موتور قدیمی آزموده و جمع‌ها را بررسی می‌کند. آزمون‌های تقویم و شناسایی اختلاف گردکردن نیز برقرارند. این آزمون‌ها فقط ویژگی‌های انتخاب‌شدهٔ نسخهٔ قدیمی را می‌سنجند؛ آزمون Kotlin parity، migration و UI نیستند.

## وضعیت دروازه

فاز صفر هنوز تکمیل نشده است: استخراج و تحلیل کامل validator و پل بومی، ماتریس همارزی برای تمام قابلیت‌ها و سناریوهای الزامی، مقایسهٔ عددی موتور Kotlin، و آزمایش روی دستگاه/DB واقعی باقی‌اند. مطابق درخواست، فاز ۱ شروع نشده است و هیچ APK جدیدی تحویل داده نمی‌شود.
