# تبدیل آزمایشی ردیف‌های قدیمی در حافظه

`data/src/main/kotlin/com/workshop/ledger/data/migration/LegacyRowConversion.kt` یک گام خالص برای آماده‌سازی تبدیل است، نه migration قابل اجرای Room. برای هر ردیف دریافت‌شده تاریخ‌های جلالی استاندارد و معتبر ۱۲۰۰–۱۷۰۰ را به ISO میلادی و مبالغ/نرخ‌های صحیح و مجاز را به `Long` تبدیل می‌کند. ستون‌های دیگر دست‌نخورده در ردیف خروجی می‌مانند؛ از جمله `valueJson` حضور، که فعلاً **بدون بازنویسی** و با رشتهٔ اصلی حفظ می‌شود. ورودی اصلی تغییر نمی‌کند. اگر هر ستون هدف ناموجود/نامعتبر، مبلغ اعشاری/خارج محدوده، تاریخ نامعتبر یا جدول ناشناخته دیده شود، به جای خروجی جزئی فهرست خطا برمی‌گردد. هیچ داده‌ای خودکار گرد یا حذف نمی‌شود.

این کد هنوز به SQLite یا Room متصل نیست و نمی‌تواند تشخیص دهد فراخواننده همهٔ ردیف‌ها و ستون‌ها را واقعاً خوانده است. نوع‌های فعلی تنها NULL، TEXT، INTEGER و مقدار عددی اعشاری‌اند؛ قرارداد خواندن بدون اتلاف SQLite REAL، مدل ذخیرهٔ نهایی، BLOB احتمالی ستون‌های ناشناخته، کلیدها و تمام قیود، بازه‌های معکوس، دسترسی هم‌زمان و تراکنش هنوز در سطح اتصال به پایگاه طراحی و آزموده نشده‌اند. همچنین باقی گذاشتن `valueJson` در این مرحله به معنی تعریف schema نهایی حضور یا اتصالش به `RecordedHours` نیست. تبدیل فقط تاریخ‌های استاندارد و معتبر را می‌پذیرد؛ برای دادهٔ خارج از این دامنه سیاست حفظ و رسیدگی هنوز لازم است. `Success` تنها موفقیت همین تبدیل محدود است، نه تأیید قابل‌مهاجرت‌بودن دیتابیس.

## آزمون

```sh
JAVA_HOME=/path/to/jdk KOTLINC=/path/to/kotlinc parity/tools/check-migration-conversion.sh
python3 parity/migration/test_preflight.py
```

آزمون Kotlin هر ده نوع جدول را با دادهٔ ساختگی، تبدیل پول و تاریخ، حفظ متن اصلی حضور ۱٫۲۵۰۰، حفظ ستون اضافی و ورودی، خطاها و تمام ۱۸۲٬۹۸۶ تاریخ golden بررسی می‌کند. آزمون Python ابزار تشخیصی جداگانه‌ای است که روی fixture مصنوعی SQL و WAL کار می‌کند. هیچ‌کدام آزمون migration ۱→۲→۳، rollback، DataStore، schema validation Room، دستگاه یا بکاپ واقعی نیستند.
