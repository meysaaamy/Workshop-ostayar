# ادامهٔ فاز صفر: مرجع جامع تقویم و آزمون مسیر ایمنی بکاپ

## مرجع روزانهٔ تقویم

`parity/golden/calendar-1200-1700.jsonl` خروجی توابع تقویم قدیمی را برای **۱۸۲٬۹۸۶ روز جلالی معتبر که اعتبارسنج وب می‌پذیرد** دارد. هر سطر، ورودی جلالی، خروجی میلادی و نتیجهٔ تبدیل برگشت را نگه می‌دارد. سرآیند هش APK و HTML و نام ستون‌ها را مشخص می‌کند. فایل با `cd parity && npm run calendar-golden` بازتولید می‌شود؛ آزمون ترتیب روزها، کبیسه‌های ۱۳۹۹ و ۱۴۰۳، رد ۳۰ اسفند ۱۴۰۲، تعداد و برابری هش فایل بازتولیدشده را بررسی کرد.

این بازه با محدودیت `cvDate` وب یعنی ۱۲۰۰ تا ۱۷۰۰ انتخاب شده است. همان‌طور که در گزارش اعتبارسنجی ثبت شده، validator بومی برای ماه ۱۲ تا روز ۳۰ را مستقل از کبیسه می‌پذیرد؛ بنابراین این مرجع صرفاً روزهای معتبر وب را پوشش می‌دهد و رفتار ایمن در برابر تاریخ نامعتبر ذخیره‌شده یا واردشده باید جداگانه طراحی و آزموده شود. آزمون ۷۸ خطای مرزی الگوریتم در خارج از این بازه نیز جداگانه حفظ شده است.

`parity/kotlin/CompareCalendar.kt` یک مقایسه‌گر streaming برای این فایل است. ورودی نتایج adapter باید JSONL باشد: سطر اول شیء `goldenSha256`، و سپس برای هر سطر مرجع به همان ترتیب یک آرایهٔ `[gy,gm,gd,jy,jm,jd]` که واقعاً توسط موتور جدید محاسبه شده است. هش فایل مرجع و APK، تمام نتیجه‌ها، کمبود و اضافه بودن سطر بررسی می‌شوند. `parity/tools/check-calendar-kotlin.sh` با کپی نتایج مرجع، تغییر خروجی ۳۰ اسفند ۱۴۰۳ و حذف یک سطر، **خود مقایسه‌گر** را آزمود؛ چون هنوز موتور جدید وجود ندارد، این آزمون همارزی تقویم جدید نیست.

## جریان ایمنی بکاپ قدیمی

`parity/tools/check-backup-safety.js` توابع اصلی وب را از APK در محیط آزمون با ذخیره‌ساز mock اجرا می‌کند. در این آزمون، شکست ذخیرهٔ نسخهٔ اضطراری باعث بازگرداندن recovery قبلی و بازگشت `false` می‌شود؛ همچنین فاصلهٔ ۱۵ دقیقه، عدم تولید snapshot برای دادهٔ بدون تغییر و نگه‌داشتن سه snapshot آخر در حافظه بررسی شدند. در آزمایش جداگانهٔ `replaceWholeState` با وابستگی‌های mock، در صورت شکست نسخهٔ امن فراخوانی ذخیره رخ نداد و در صورت شکست ذخیره، وضعیت قبلی در حافظه بازگردانده شد. این آزمون **اثبات دوام ذخیره روی Room/DataStore، رفتار واقعی دستگاه یا بازیابی SAF نیست**؛ بررسی بعدی نشان داد Room و DataStore در دو مرحلهٔ جدا نوشته می‌شوند ([جزئیات](phase-0-native-storage-fa.md))؛ همهٔ این‌ها همچنان به تست فازهای بعد و DB واقعی نیاز دارند.

## دستورها و وضعیت

```sh
cd parity && npm ci && npm test
JAVA_HOME=/path/to/jdk KOTLINC=/path/to/kotlinc ./tools/check-calendar-kotlin.sh
```

آزمون‌های بالا با ابزارهای موقت محیط اجرا و موفق شدند. علاوه بر این، ۶۶۶ سناریوی مرجع عمومی و مقایسه‌گر عمومی قبلی حفظ شده‌اند. فاز صفر هنوز بسته نشده: تحلیل و نگاشت کامل ویژگی‌ها، بقیهٔ سناریوهای مرجع و شواهد لازم از کلاس‌های بومی باقی است. هیچ موتور، مهاجرت یا APK جدیدی ساخته نشده و فاز ۱ آغاز نشده است.
